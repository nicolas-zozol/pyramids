# Design: ramener les adresses v1 en redirections permanentes

**Last update:** 2026-11-06
**Feature:** restore-v1-urls
**Infix:** RESTOREV1
**Status:** IMPLEMENTED (2026-11-06, commit 467beaa)
**Sources:** [story](restore-v1-urls.story.md), [brainstorm](restore-v1-urls.brainstorm.md), [epic](../../pyramid-v2.epic.md), [seo-url-scheme](../seo-url-scheme/seo-url-scheme.design.md), [tanstack-start-migration](../tanstack-start-migration/tanstack-start-migration.design.md)

## Goal

Une nouvelle étape de `build`, `scripts/emit-redirects.mjs`, traduit la v1 map en règles Netlify et les écrit dans `dist/client/_redirects` après `vite build` : 67 permanentes en 301, 5 Gone en 410 et 5 sans destination sous `/learn` en 404, les deux derniers groupes servant `/404.html`. Elle échoue quand une destination n'est pas une page construite. Dans le package `routing`, la ligne image de la map se scinde en ses deux formes v1. Le pourquoi : [story](restore-v1-urls.story.md).

Les adresses v1 reviennent en rattrapage de v1 seulement : aucune BR, et un article v2 renommé change d'URL sans redirection. Les règles Gone sont écrites en 410 ; si le draft deploy montre que Netlify Free sert 404, ces adresses restent en 404, sans fonction ni page dédiée.

## Boundaries

```
  Arrow = depends on, from client code to the API it uses.
  Packages of app `@robusta/robusta-build`. No loop.

  yarn build
      │ CLI
      ↓
  package `scripts` [modified: emit-redirects]
      │                          │
      │ library                  │ library
      ↓                          ↓
  package `routing`  ──library──→  package `content`
  [modified: v1 map image rows]

  Netlify reads dist/client/_redirects, written by `scripts`.
```

`content` ne change pas : `emit-redirects.mjs` y lit `getArticleIndex()`, comme `emit-v1-map.mjs` et `emit-site-files.mjs`. Rien ne dépend de `scripts`.

### HTTP API of app `@robusta/robusta-build` — modified

Client code : robots des moteurs, visiteurs venant d'un lien v1.

```
GET <adresse v1 permanente>[/]        → 301, Location : la page v2 de la map, déjà canonique ; la query string suit
GET <fichier markdown v1 Gone>        → 410, corps 404.html
GET /learn/page/:n, /learn/fr/page/:n,
    /learn/tag/:tag/page/:n,
    /learn/images/:file,
    /learn/:category/s/images/:file   → 404, corps 404.html
GET /learn/<tout le reste>            → 410, corps 404.html
GET robusta-build.netlify.app/<v1>    → 301 sur cet hôte, puis 301 vers www
GET <toute adresse v2>, /en…          → inchangé
```

- Servi par Netlify seul, depuis `dist/client/_redirects` : aucune fonction, aucune lecture du corpus à la requête (BR-PYRAMID-7).
- Une adresse v1 répond dans la casse que v1 a publiée, et dans aucune autre : `/learn/tag/DeFi` a sa destination, `/learn/tag/defi` tombe sur `/learn/*`.
- Si le draft deploy montre que Netlify sert 404 là où la règle dit 410, les adresses Gone répondent 404 et la règle reste écrite en 410.
- Sous `vite dev`, aucune règle : une adresse v1 répond par la page 404.

### CLI API of package `scripts` — new step of `build`: `emit-redirects.mjs`

Client code : `yarn build` (`package.json` de l'app), donc `yarn build:robusta` et la build Netlify.

```
node scripts/emit-redirects.mjs
  lancé par   `build`, après emit-site-files.mjs, avant check-seo.mjs
  lit         v1UrlMap(urlScheme, await getArticleIndex()), les fichiers de dist/client
  écrit       dist/client/_redirects : une ligne d'en-tête `# generated by scripts/emit-redirects.mjs from the v1 map`,
              puis une règle `<from> <to> <status>` par ligne servie, dans l'ordre de la map
  stdout      redirects: <n> rules (<p> permanent, <g> gone, <x> not found) → dist/client/_redirects
  exit 1      sur stderr, une ligne par défaut, et aucun fichier écrit :
                <from>: destination <to> is not a built page
                <from>: no Netlify form for this source
                404.html: not built, the gone and not-found rules have no page
```

Traduction d'une ligne `V1MappingRow` :

- `permanent` → `<from> <to> 301`
- `gone` → `<from> /404.html 410`
- `none` dont `from` vaut `/learn` ou commence par `/learn/` → `<from> /404.html 404` ; toute autre ligne `none` n'a pas de règle
- `from` est recopié tel quel, casse comprise ; `:name` reste un placeholder d'un segment ; un `/:name*` final devient `/*` ; un `*` ailleurs est le défaut `no Netlify form`
- aucune règle n'est forcée (pas de `!`)

Une destination est une page construite quand `dist/client` contient `<to sans le / initial>.html`, ou `index.html` pour `/` : la lecture inverse d'`urlOfHtmlFile` de `check-route-table.mjs`. `404.html` n'est jamais une destination de 301.

Seam testable, exporté par le script comme `siteFiles` et `seoReport` le sont par les leurs :

```ts
type V1MappingRow; // package routing, inchangé

type RedirectsFile = {
  text: string;       // le contenu de _redirects, vide quand defects ne l'est pas
  defects: string[];  // une ligne par défaut, format ci-dessus
  summary: string;    // la ligne stdout
};

/** The `_redirects` of the v1 map over the files `vite build` wrote, or its defects. */
function redirectsFile(input: { rows: V1MappingRow[]; files: string[] }): RedirectsFile;
```

Client code, dans `scripts/emit-redirects.spec.ts` :

```ts
import { redirectsFile } from './emit-redirects.mjs';

const { text, defects } = redirectsFile({ rows: v1UrlMap(urlScheme, index), files: builtFiles });
expect(defects).toEqual([]);
expect(text.trimEnd().split('\n').at(-1)).toBe('/learn/* /404.html 410');
```

### library API of package `routing` in app `@robusta/robusta-build` — modified

Client code : `emit-v1-map.mjs`, `emit-redirects.mjs`, `v1-url-map.spec.ts`.

```ts
type UrlScheme, ArticleIndexEntry, V1MappingRow, V1Destination; // inchangés

/** Every v1 address, led to the page `scheme` builds in the language of its v1 page. */
function v1UrlMap(scheme: UrlScheme, articles: readonly ArticleIndexEntry[]): V1MappingRow[]; // signature inchangée
```

Seules les lignes changent : `/learn/:path*/images/:file` devient `/learn/images/:file` puis `/learn/:category/s/images/:file`, à la même place, `none` avec la même raison. Sur le corpus réel : 83 lignes, 67 `permanent`, 5 `gone`, 11 `none`, `/learn/:path*` toujours en dernier.

## Technical Constraints

- Netlify, offre Free, publication de `dist/client` : `_redirects` à la racine publiée est lu avant les `[[redirects]]` de `netlify.toml` ; la première règle qui correspond gagne ; une règle sans `force` cède au fichier existant au chemin demandé, ce qui protège toute page v2 (AC-RESTOREV1-3) et garantit le saut unique, chaque destination étant un fichier construit. Les placeholders `:name` valent un segment, le splat `*` n'existe qu'en fin de chemin : d'où la scission de la ligne image. Une règle correspond avec ou sans barre finale. Les chemins sont sensibles à la casse ; la redirection en minuscules de l'hôte ne joue que si le fichier en minuscules existe, jamais sous `/learn`. Statuts documentés : 200, 301, 302, 404 ; le 410 ne l'est pas. Netlify transmet la query string à la destination d'un 301. Sources : le brainstorm §9 et [tanstack-start-migration](../tanstack-start-migration/tanstack-start-migration.design.md), Technical Constraints.
- `vite build` vide `dist/client` : l'étape ne peut tourner qu'après lui. Aucun `public/_redirects` : Vite le copierait, et la build l'écraserait.
- `emit-redirects.mjs` charge les seams `.ts` de `src` par le type stripping de Node, comme `emit-site-files.mjs` (Node 22.18 au minimum).
- Le draft deploy du CLI (`npx netlify-cli deploy`, jamais `--prod`) sert les mêmes règles sous `<id>--robusta-build.netlify.app`, que la règle d'hôte ne vise pas. Les deux sauts depuis `robusta-build.netlify.app` ne se constatent qu'en production.
- 77 règles, loin de toute limite de taille de `_redirects`.

## Requirements

### Règles générées

- R-RESTOREV1-01 : `scripts/emit-redirects.mjs` calcule `v1UrlMap(urlScheme, await getArticleIndex())` et écrit `dist/client/_redirects` ; le script `build` de `package.json` le lance après `emit-site-files.mjs` et avant `check-seo.mjs`.
- R-RESTOREV1-02 : une règle par ligne servie, dans l'ordre de la map : toutes les lignes `permanent` et `gone`, et les lignes `none` situées sous `/learn` ; la règle de `/learn/:path*` est la dernière du fichier.
- R-RESTOREV1-03 : `permanent` donne un 301 vers `to`, `gone` un 410 vers `/404.html`, `none` sous `/learn` un 404 vers `/404.html` ; aucune règle forcée.
- R-RESTOREV1-04 : `from` est recopié dans sa casse ; un `/:name*` final devient `/*`, les autres placeholders restent.
- R-RESTOREV1-05 : `netlify.toml` garde ses trois règles ; son commentaire d'en-tête nomme `_redirects`, que la build écrit et que Netlify lit avant lui. `dev` ne change pas.

### Garde de build

- R-RESTOREV1-21 : une destination `permanent` qui n'est pas une page construite de `dist/client` fait sortir le script en 1, une ligne par ligne fautive, sans écrire `_redirects` (AC-RESTOREV1-4).
- R-RESTOREV1-22 : une source qu'aucune forme Netlify n'exprime, et l'absence de `404.html`, sont des défauts du même format.
- R-RESTOREV1-23 : sans défaut, le script écrit sur stdout sa ligne de compte : 77 règles, 67 permanentes, 5 Gone, 5 not found sur le corpus réel.

### v1 map

- R-RESTOREV1-41 : `imageRows()` rend deux lignes, `/learn/images/:file` et `/learn/:category/s/images/:file`, les deux formes des dossiers d'images de v1 ; `V1_INVENTORY` et les comptes de `v1-url-map.spec.ts` passent à 83 lignes, 67/5/11 ; `v1-url-map.generated.json` est régénéré.
- R-RESTOREV1-42 : la `note` de la ligne `/learn/:path*` dit qu'elle est servie par la dernière règle de `_redirects` ; l'en-tête de `emit-v1-map.mjs` ne dit plus que rien ne sert la map.
- R-RESTOREV1-43 : `v1UrlMap`, `V1MappingRow` et `V1Destination` gardent leur forme ; aucune redirection n'est écrite pour un article v2 renommé.

### Constat sur l'hôte

- R-RESTOREV1-61 : avant le merge, un draft deploy est éprouvé par une passe manuelle de `curl -I` sur une adresse de chaque classe des edge cases ci-dessous : statut, `Location`, puis 200 sur la destination. Aucun script de constat n'est commité : les règles ne changent pas d'un deploy à l'autre et la spec de `emit-redirects.mjs` couvre le fichier. Il constate le statut servi par la règle Gone : 410, ou 404 sans fonction ni page dédiée si Netlify Free ne sert pas le 410.
- R-RESTOREV1-62 : après le merge, le double saut depuis `robusta-build.netlify.app` est constaté en production, à `storyman done`.

## Acceptance Criteria

- AC-RESTOREV1-1 : Given une adresse v1 que la map mène à une page v2, When un visiteur ou un robot la demande sur www.robusta.build, Then il reçoit une redirection permanente vers cette page, en un seul saut, et la page répond 200.
- AC-RESTOREV1-2 : Given une adresse v1 marquée Gone par la map, un fichier markdown retiré ou une adresse `/learn/…` qu'aucune ligne ne réclame, When on la demande, Then elle répond 410 avec la page introuvable, ou 404 si Netlify Free ne sert pas le 410 ; Given une adresse v1 sans destination, image v1 et page de roll v1 sous `/learn` comprises, Then elle répond 404 avec la page introuvable, comme aujourd'hui, et non 410.
- AC-RESTOREV1-3 : Given les pages v2 et les redirections `/en…` existantes, When les redirections v1 sont servies, Then aucune adresse v2 ne change de réponse.
- AC-RESTOREV1-4 : Given un article qui change de category ou un nouvel article, When le site est construit, Then les redirections servies suivent la map sans édition à la main ; une redirection dont la destination n'est pas une page construite fait échouer la build.
- AC-RESTOREV1-5 : Given les cas limites, When on les demande, Then un article français que v1 publiait sans marqueur de Locale mène à sa page française ; `/learn/fr/blockchain/`, avec sa barre finale, mène à la même page que sans ; `/learn/tag/DeFi`, avec sa casse v1, a sa destination, et `/learn/tag/defi`, que v1 n'a jamais publié, répond comme une adresse Gone ; un fichier markdown brut v1 mène à la page de son article ; un article v1 dépublié ou dont le titre change laisse la build aboutir, et son adresse v1 comme son fichier markdown brut répondent comme une adresse Gone, sans redirection vers un nouveau slug ; une adresse v1 demandée sur `robusta-build.netlify.app` aboutit en 200 à sa page sur www.robusta.build, en deux redirections permanentes.

Edge cases to test, où Gone se lit 410, ou 404 si Netlify Free ne sert pas le 410 :

- `/learn/blockchain/s/provenance-des-rendements-du-yield-farming-dans-la-blockchain`, article français publié par v1 sans marqueur : 301 vers sa page sous `/fr/articles/…`.
- `/learn/fr/blockchain` et `/learn/fr/blockchain/` : même `Location`, `/fr/articles/c/blockchain`, un seul saut.
- `/learn/tag/DeFi` : 301 ; `/learn/tag/defi` : Gone.
- `/learn/blockchain/s/ledger-versus-metamask.md` : 301 vers la page de l'article ; `/learn/javascript/s/es6-7.md` : Gone.
- `/learn/n-importe-quoi` : Gone ; `/learn/page/2`, `/learn/tag/web/page/2`, `/learn/images/{fichier}`, `/learn/blockchain/s/images/{fichier}` : 404, jamais 410.
- Sur fixture, un article v1 absent de l'index, dépublié ou renommé : build verte, aucune ligne d'article, sa ligne markdown en `gone`, donc Gone.
- Sur fixture, un `dist/client` privé d'une page destination : exit 1, la ligne nomme la source et la destination, aucun `_redirects`.
- `/learn/blockchain?utm_source=x` : la query string suit le 301.
- `/`, `/articles`, `/fr/articles/c/blockchain`, `/en/articles` : réponse inchangée.
- `https://robusta-build.netlify.app/learn/blockchain` : 301 sur cet hôte, 301 vers www, 200.
